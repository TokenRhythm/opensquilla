## 关联修复：#1445（压缩链路记账守卫）

建了姊妹 PR **#1445**，与本 PR 联动解决同一问题域——两者互补、互为前提，合流后防线才闭环。

### 分工

| 层面 | 本 PR（#1407 水位治理） | #1445 记账守卫 |
|---|---|---|
| 关注点 | 历史**怎么长胖**：工具结果全量内联、增长不可见 | 长胖之后：token 账本**是否真实**、压缩执行过程**会不会伤人** |
| 手段 | 工具结果水位投影 + 会话水位告警 | 写入端记账口径修复 + 读取端封顶 + 兜底拒绝毁摘要 + 降级 warning 可见 |

### 为什么必须联动

实际事故链复盘（详见 #1445 正文）：一条 assistant 条目自身可回放体量约 22K token，持久化 `token_count` 却被记成 770,191（整轮累计输出被抄进了单条记录）；回放估算无条件信任账面，某会话账面合计约 165 万 token，而真实字符总量约 17 万（真实水位约 5%）。后果有两个直接落在本 PR 的地盘上：

1. **「85% 自动预检压缩」正是被这本虚高的账推着提前触发的**——干预点本身失真；
2. 压缩 LLM 因输出预算守卫连续失败后，确定性兜底用一个 ~68 token 的存根摘要整体替换了 170,864 字符的结构化检查点，全程仅 INFO 日志——即使干预及时、正确，执行链条本身也可能摧毁数据。

所以：#1407 让干预发生在膨胀途中且对用户可见；#1445 保证触发干预的那把尺子是准的、执行干预的过程有底线、异常结局必然可感知。两边任缺其一，防线都有洞。
