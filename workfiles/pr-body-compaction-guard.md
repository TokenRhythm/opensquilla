# fix(engine): 压缩链路记账守卫——防虚高 token 记账与降级丢摘要

关联 PR：#1407（上下文水位治理）。两个 PR 联动解决同一问题域：#1407 治「历史怎么长胖」，本 PR 堵「长胖之后压缩过程本身会不会伤人」。详见下文方案一节末尾的分工说明。

## 问题

实测事故（webchat 长会话）：一条 assistant 条目自身可回放内容仅约 22K token（tool_calls 序列化约 87K 字符），持久化 `token_count` 却记成了 **770,191**——完全等于该回合的整轮累计输出（含几十条重试腿）。由这条错误记录触发了一串连锁：

1. **写端记账口径错误**——条目持久化时消息级 `message_output_tokens` 缺失即回退抄录 `done_event.output_tokens`。多腿重试回合里这是整轮累计值，不是该条目自身的体量，抄入持久化账本后造成系统性虚高；
2. **读端无条件信任账面**——回放估算取 `max(持久化 token_count, 字符估算)`，虚高值直接赢。实测该会话 119 条归档记录账面合计约 165 万 token，而真实字符总量约 17 万（≈4 万 token，真实水位约 5%）。预检据此误判「85% 撞线」，在健康水位提前触发压缩；
3. **压缩 LLM 失败后兜底整体替换旧摘要**——两次压缩尝试均被输出预算守卫掐断后，确定性兜底用一个 ~68 token 的存根摘要**整体替换**了 170,864 字符的结构化检查点摘要，且无任何阻断直接 commit，会话结构化状态被摧毁；
4. **降级全程静默**——以上过程只有 INFO 级日志，问题只能靠事后从现象倒推发现。

每个环节单独看都不致命，但缺任何一环都不会发生实际丢数据：没有 1/2 就不会提前触发压缩；没有 3 兜底也只是多压一次；没有 4 至少当场可知。

## 方案：四道守卫

### 写端：单腿真值优先 + 多腿虚高挡板（turn_finalizer_stage.py）

- `message_output_tokens` 保持最高权威，行为不变；
- 回退分支不再无脑抄整轮累计：累计值超过该条目自身回放体量 **4 倍**即判定为多腿虚高，改信按条目内容序列化的回放估算；否则取两者较大值——既挡住 77 万级别的虚高抄账，又不牺牲正常单腿回合的真值精度（这条边界来自回归驱动：仅 3 token 的单腿输出曾被第一版方案错降为估算值 1）。

### 读端：持久化 token_count 封顶（compaction.py)

- 一个 token 至少解码一个字符，因此持久化值若高于「条目全量序列化回放体量 + 余量」，即可证明它描述的不是这条目本身；
- 两个消费入口统一在读取端封顶，存量虚高行无需迁移即在内存中被中和。

### 兜底安全网：禁止毁掉富摘要

确定性兜底在存在实质性旧摘要（≥1000 字符，含结构化状态区块）时**拒绝提交**（skip_reason=`fallback_degraded_with_prior_summary`），不再以存根覆盖结构化历史；残余压力交给既有的压力路径消化。

### 降级可见性

压缩终态事件中的降级结局提升为 warning 级日志，与 #1407 的告警思路一致：异常必须可见，不能只留事后倒推。

### 与 #1407 的联动分工

| 层面 | #1407 | 本 PR |
|---|---|---|
| 关注点 | 历史如何长胖：工具结果全量内联、增长不可见 | 长胖后的账本是否真实、压缩失败会不会伤人 |
| 手段 | 工具结果水位投影 + 水位告警 | 记账口径守卫（写入端 + 读取端）+ 兜底保护 + 降级可见 |

两者互补而非重叠：#1407 让干预发生在膨胀途中，本 PR 保证触发干预的那把尺子（token 账本）是准的、执行干预的过程有底线。

## 验证

- 新增 8 例回归（两个独立测试文件，不触碰既有测试锚点）：
  - 整轮累计输出不得抄入条目 token_count / 单腿真值精度保持；
  - 封顶不会误伤合法的大 payload（40 × 2KB tool_calls 全额计入，上限之上才拦）；
  - 虚高账面行读取端被中和 / 合理账面原样保留；
  - 存在富摘要时兜底拒绝提交 / 小存根场景不受影响；
  - 降级结局 warning 级可见。
- 相关存量回归全绿：finalizer 单测、compaction 全族、provider 运行时共 113 passed；
- 爆炸半径扫描 `tests/test_session` + `tests/test_engine/turn_runner` 共 1210 例：1208 过 / 1 skip / 1 失败，唯一失败用例在纯 upstream/main 基线上同样失败（上游存量故障，与本改动无关）。
