# feat(engine): 上下文水位治理——历史工具结果投影与会话水位告警

## 问题

长会话历史单调增长且缺乏过程刹车：工具结果全量内联进历史，会话可以持续膨胀直到超过路由链上所有可用上下文窗口。

实测案例：某个 webchat 会话单轮输入达 **1,777,402 token**（缓存命中 1,603,264），超过链上最大 1M 窗口后，自动压缩在数学上已不可能成功（受保护近期尾部 + 系统提示本身已超预算），用户只在请求时收到 `request is too large` 的 SystemError，会话不可恢复、只能废弃。

现有绝对/聚合压缩通道只在**请求级预算压力出现后**才动作，且已全文投递过的块被冻结不再处理——增长过程中没有任何可见信号与提前干预点。

## 方案：两层治水

### 1. 历史工具结果水位投影（`agent.py`）

新增确定性请求视图投影 `_compact_history_tool_results_for_provider`：当历史跨越超过
`tool_result_history_projection_keep_recent_turns`（默认 3）个已完成助手回合后，
将超过单结果上限的成功非工件 tool_result 在请求视图中替换为「预览 + handle」信封：

- 不依赖聚合压力出现，也不受冻结状态限制；
- 最近回合不受影响；持久化 transcript 原文永不修改；
- 原文可随时通过既有 projection-handle 检索路径取回，信息零丢失。

### 2. 会话水位告警（`runtime.py`）

预检压缩的无压力分支新增一次性提醒：持久历史跨过活跃窗口的
`context_waterline_alert_ratio`（默认 0.70）且未触发自动压缩时，向会话写入一条系统消息
（建议 /compact 或新开会话）：

- 每次跨越只提醒一次（按会话锁存）；任何持久压缩或压力回落即清锁存；
- best-effort：告警失败绝不阻塞回合。

两者分工：投影管住"历史里最大的东西"，告警管住"整体水位的可见性"，85% 自动预检压缩照旧兜底。

## 验证

- 新增 9 个测试：
  - 投影 4 例——冻结老块被投影 / 近 3 回合保护 / 开关关闭 / 短历史跳过；
  - 告警 5 例——单次发射 / 跨线→压缩→再涨再告警完整生命周期 / 线下清锁存 / 冷启动超线不误报 / 存储故障隔离；
- 相关回归全部通过：水位+预检 63、压缩族 130、网关配置 455；ruff 无告警。
