# Constraint-Aware Memory：实现复审（2026-07-30）

> 状态：实验性，所有新增推理行为默认关闭。
> 范围：本 PR 自身的逻辑设计、真实实现、成本、稳定性与可用性。

## 结论

当前实现遵守两条核心边界：

1. compaction 在资源耗尽时优先恢复 liveness，并用结构化 summary、
   archived transcript 与可选 anchor 尽量减少不可逆损失；
2. memory 在资源充足时改善信息组织，但分类、路由、coverage advisory、
   usage tracking、Dream 与 anchor 均保持可关闭、可降级。

“coverage 不足时永不压缩”和“资源耗尽时一定恢复可运行”在边界条件下
不能同时保证。本实现选择 liveness 优先；coverage 是 advisory，不是
阻断条件。压缩的工程目标是针对后续推理目的保留信息效用，而不是保证
字面等价或形式化语义等价。

## 本轮发现并修复

### 1. 设置开关的生效语义不诚实

`memory.experimental` 四个标志在启动时复制到 store/retriever。之前
config patch 虽会更新内存配置对象，却不会改变已构造的运行实例，而且
回执错误地声称实时生效。

修复后，这四个字段进入 memory restart fingerprint；前端明确标记需重启。
`compaction.anchor_enabled` 由每次 turn/compaction 读取，仍从下一次压缩
实时生效。

### 2. Agent 内部 compaction 配置链不完整

gateway preflight 与 session RPC 会传递完整 compaction 配置，但 Agent
内部 overflow 路径此前只继承 profile 和 protected tail，遗漏：

- `anchor_enabled`
- `fallback_summary_max_tokens`
- `previous_summary_max_tokens`
- `total_summary_max_tokens`

这会使同一会话因触发入口不同而产生不一致行为。现已贯通 TurnRunner →
AgentConfig → Agent compaction，并保证 child agent 继承相同策略。

### 3. 文档与真实 L3 依赖不一致

L3 与 L2 共享 intent classifier，但 intent outcome 已是 request-scoped；
L2 或 L3 任一开启都会分类，只有 L2 修改排序。因此 L3 可独立开启。
旧文档中“L3 仅在 L2 开启时可用”的描述已修正。

### 4. 前端缺少实验性控制面

`Settings → Advanced → Memory & self-learning` 现可控制：

| 开关 | 配置路径 | 生效时机 |
|---|---|---|
| Constraint annotation | `memory.experimental.constraint_annotation` | 重启后 |
| Constraint-aware retrieval | `memory.experimental.constraint_routing` | 重启后 |
| Retrieval coverage warning | `memory.experimental.sufficiency_check` | 重启后 |
| Recall usage tracking | `memory.experimental.usage_tracking` | 重启后 |
| Recoverable compaction anchors | `compaction.anchor_enabled` | 下一次 compaction |

所有开关默认关闭，前端只通过 operator-write 的 safe boolean allow-list 写入；
阈值、模型、schedule 和 token budget 仍保持 admin-only。

## 成本审计

### LLM 推理开销

- L1 是主要新增成本：仅对新增/变化且 signal gate 通过的 chunk 分类；
  并发上限为 4，按完整 chunk hash 使用 4096 项进程内 cache。provider
  不可用或失败时降级到本地 heuristic。
- L2 与 L3 复用本地 intent 分类，不额外调用 LLM。
- D11 仅做有界后台 SQLite 写入，不占用 turn 的关键路径。
- D12 增加 anchor instruction、entry label 和少量 summary token；summary
  仍受 fallback/previous/total 三层预算约束。
- Dream 仍是独立 opt-in 的定时模型调用，preview 与 auto-schedule 分开控制。

因此默认配置没有新增模型开销；启用 L1 时首次重索引可能形成明显的短时
调用峰值，设置文案对此作了提示。

### 执行复杂度

- retrieval outcome 改为 request-scoped，消除了并发查询共享状态。
- compaction identity 由数据库派生并在写事务内复核，避免并发编号漂移。
- fork 的 SQLite lineage copy 与 child row 创建在同一事务提交。
- `MEMORY.md` 更新使用同路径锁、内容 CAS 与原子替换。
- Dream 使用递归扫描、完整内容 hash 与 `(mtime_ns, path)` 复合 cursor。

新增复杂度集中在边界适配、事务和显式状态中，没有引入新的持久化完整性
状态机。anchor 的三态只存在于 lookup 路径：`RESOLVED`、
`DECLARED_UNAVAILABLE`、`UNKNOWN`。

## 稳定性与可用性影响

正面影响：

- 资源压力下不会因 coverage advisory 阻断 liveness；
- compacted evidence 可搜索，可选 anchor 提供精确恢复入口；
- fork、Dream cursor、MEMORY.md apply 与 compaction index 的失败边界更原子；
- 设置界面显示真实的生效时机，且实验性功能仍默认关闭。

代价与剩余限制：

1. L1 首次启用会因 annotation schema version 变化触发重索引；大型 memory
   集合应预期一次性模型成本与启动后索引延迟。
2. classification cache 仅在进程内；重启后的冷 cache 不会复用旧调用结果，
   数据库中已标注且未变化的 chunk 仍不会重复分类。
3. D11 在并发任务达到上限时选择丢弃统计以保护检索延迟；当前只有日志，
   没有专用 drop metric。
4. D10 依赖文件系统 mtime 游标。正常写入安全；如果外部工具在改变内容时
   强行保留旧 mtime，该文件可能要等 cursor reset 或再次修改后才被扫描。
5. 启用 D12 不回填旧 summary；旧 compaction 会自然成为
   `DECLARED_UNAVAILABLE`，不是 `UNKNOWN`。
6. anchor 是恢复能力而不是完整性证明。summary token 预算可能保留一部分
   而非全部 anchor；最终只持久化能解析且落在本次 archived entry 范围内的
   引用。
7. `UNKNOWN` 正常情况下应稀少：它通常表示调用方提供了从未声明的 anchor，
   或暴露新的 lineage/数据完整性问题。lookup 返回明确错误，不把“不知道”
   伪装成“不存在”。

这些限制不阻塞实验性发布，但其中 1、3、4 值得在扩大默认启用范围前加入
运营指标与压力验证。
