# Windows 客户端性能对照：2026-09-29

本轮确认了两条忙碌 I/O 路径的响应性收益，**没有证明正常启动、重启普遍提速**。完整复杂组和普通组的各十对测试均通过；首次复杂组另有一条未归因失败，保留在下文。签名安装更新不在本轮范围内。

## 固定条件

- 基线是分支合入的 main 快照 `0c24dfde0f2cae7cd4d3074ebd5a409f53fd4ce1`，候选是 `4c2409aaec327765249ba0f845ebeb0eec608708`。这是两个固定源码包的比较，不是与 issue 报告中的已发布版本比较，也不是与此后变动的远端 main 比较。
- 本机 Windows build 26200、Core Ultra 7 255H、约 32 GB RAM；相同依赖锁、Python 3.12.13、Electron 42.11.4，未签名解包目录。完整 Gateway 输入及包输出、Electron 编译内容、WebUI 和关键组件 hash 均核对。没有更改 Defender、产品超时或真实用户 profile。
- 两版均 `--disable-gpu`，正式对照关闭可选启动计时；串行运行，按 AB/BA 交替十对，测试期间不并行构建或压力负载。OS 缓存不清空，校验包和数据库会预热缓存，故只能称新进程、已准备 profile 的启动。
- 复杂组复用已构造的 225 万小文件 lab：2106 个 session、220208 条 transcript、104 个 task、104 个 turn receipt、48 条 migration ledger。此次不重新递归统计文件；历史验收读取目标会话最新一页，不渲染全部历史。多数功能被关闭，不能代表所有真实重度用户。
- 普通组两版分别使用合成 profile，初始化和预热不计入正式样本。每轮 UI 新增一条会话，每对开始数量严格相等，正式测量由各 2 条增长至各 12 条；两库并非字节相同。Provider 为本地合成服务，首条发送发生在重启之后。

## 启动和重启结果

以下为每版十次正式样本。UI 可用要求真实连接和可编辑输入框，重启还要求新 Gateway、原页面重连和旧实例退出。单位秒；配对差值为候选减基线，负数表示候选更快。配对差值中位数不等于两组中位数之差。

| 场景 | 基线中位数 | 候选中位数 | 配对差值中位数 | 候选更快对数 |
|---|---:|---:|---:|---:|
| 复杂 profile：启动到 UI 可用 | 7.834 | 8.088 | -0.166 | 5/10 |
| 复杂 profile：重启到 UI 可用 | 9.758 | 9.550 | -0.313 | 5/10 |
| 普通 profile：启动到 UI 可用 | 7.664 | 7.915 | +0.114 | 4/10 |
| 普通 profile：重启到 UI 可用 | 7.778 | 7.585 | -0.613 | 6/10 |
| 普通 profile：重启后发送到回答可见 | 0.798 | 0.791 | -0.039 | 7/10 |
| 普通 profile：点击历史到读取且可见 | 0.205 | 0.214 | +0.011 | 3/10 |

两组启动中位数都略高、重启中位数略低，配对存在明显双向波动。复杂组启动配对差值范围为 -1.585 至 +4.008 秒，重启为 -2.184 至 +3.139 秒；不能挑较快样本宣传提速。复杂组重启后历史点击中位数由 0.786 变为 1.028 秒，6/10 对更慢，保留为未解释观察，不能概括为所有交互完全无回退，也不足以归因于某项代码改动。

复杂组 2 次预热及 20 次正式运行、普通组 2 次初始化、2 次预热及 20 次正式运行，全部通过各自业务和自然退出检查。复杂组的配置、数据库稳定字段、迁移、schema、index、layout 摘要前后相同，owner 清空；普通组每轮一条发送对应一个 Provider 请求、历史回读通过、flow 故障为零。它们说明这些运行成功，不能推导产品长期失效率、可靠 p95 或 issue #1821 已修复。

## 已证实的忙碌响应性收益

另用两个包的真实 frozen 函数，各做三次独立实验：owner SQLite 写库遇到测试线程持有的约四秒写锁；以及删除 disposable session 的 12000 个额外小文件。没有 mock 产品 I/O，没有修改产品超时。使用 10ms 心跳观察同一 asyncio loop 的最大调度迟滞。

| 场景 | 基线各次最大调度迟滞范围 | 候选范围 |
|---|---:|---:|
| owned subprocess 登记遇 SQLite 写锁竞争 | 3324–3572 ms | 12–23 ms |
| session 材料物理删除 | 2007–4883 ms | 11–14 ms |

所有场景的业务、owner/claim 清空、精确 Windows 子进程退出、相邻材料保留均通过。操作总耗时仍有重叠：写锁和磁盘工作没有消失，收益是等待期间不再把事件循环堵住。这支持保留登记与材料清理移出事件循环的修改。

这组直接 frozen 机制实验没有启动 Gateway listener 或 WebSocket，数字不是网络请求延迟、断线率或 UI 延迟。登记后取消也不能代替登记中取消的源码回归测试。

## 剩余启动耗时的定位

复杂组候选版正式样本的现有日志显示，首开/重启从 Gateway spawn 到 Desktop 观察健康的中位耗时为 5.134/5.874 秒，进入 `run_gateway` 到内部 ready 为 0.547/0.742 秒，其中 services 为 0.203/0.235 秒。前段有较大未细分成本。日志关联依赖已验证的独占实例和时间窗口，跨进程墙钟推算不能当作共享单调时钟。

随后仅候选版单独开启本地 startup timing，完成一次首开和重启，历史、退出及数据保留检查通过；不加入上述 A/B 样本。该次 CLI import 约 3.50/3.11 秒，其中命令模块导入约 3.49/3.09 秒；最终持锁 profile inspection 约 0.91/2.06 秒；进入 Gateway 主流程到内部 ready 两次均约 0.69 秒。CLI 导入与命令导入是包含关系，不能累加。

这为下一步提供两个明确定位入口：

1. `src/opensquilla/cli/main.py` 的命令模块集中导入。先区分 Gateway 必需的共享依赖与本次启动不需要的命令依赖，再评估最小延迟导入；不能把观测到的三秒全部许诺为可省时间，也不能把成本转移到首次发送。
2. `src/opensquilla/recovery/engine.py` 的 `guarded_desktop_profile → inspect_profile`。其数据库安全路径会复制数据库及现存 WAL/journal 到私有临时副本并 fsync，在副本上运行 quick_check、读取迁移账本，再重新读取源文件验证摘要。先拆解这些操作在此次检查中的占比，再消除已证明的重复工作。保留 Gateway 最终持锁检查、profile 互斥和恢复门槛；不能因 Desktop 先检查过就直接跳过，也不能将其全部归因于 225 万文件扫描。

不需要据此替换 WebUI、增加常驻服务或重做客户端架构。本轮没有新增产品优化代码，只补测量和验收。完整更新仍需独立验证下载、校验、退出、安装、迁移及更新后第一次可用，解包重启不能替代它。

## 原失败、验收脚本与证据边界

第一次复杂 A 批在完成八对后，第九对基线于重启后的历史读取验收超时，cleanup 又记录未定位的 AssertionError。随后独立审计确认两个已记录 Gateway 在审计时已退出、稳定数据保留，但没有还原失败根因，因此仍记录为失败。发现的测试缺陷包括按 sidebar 行号点击会遭遇重排、仅 URL 到达草稿页不足以证明旧会话已离开。修正为稳定 session key 定位与完整空白草稿等待后，重新执行完整 B 批，保留原 A 批，不替换个别失败或慢样本；B 通过不能追认 A 根因已解决。

可复用 harness 的新增 repeat-profile 模式只允许固定的仓库内合成目录，使用显式初始化、排他锁、干净标记、配置/凭据 hash、仅本轮日志后缀和逐轮会话数量约束。失败保留资料并停止，不自动重置。没有放宽真实新连接、目标 RPC、内容、flow、进程身份或自然退出要求。26 项纯合同测试通过；另一次独立 `history-streaming-restart` 原生回归通过，覆盖共享草稿和历史定位修改在流式场景的使用。未据此声称重跑所有其他原生场景。
