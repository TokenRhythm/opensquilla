# Sidebar Project and Recents Hierarchy Design

## Goal

Present **Projects** and **Recents** as peer sections in the sidebar, with each
section showing only its own item count, while preserving the existing project
membership, ordering, pinning, dragging, and persistence behavior.

## Current behavior and root cause

`arrangeSidebarSections` already produces the correct order for persisted
projects: project headers and their sessions come first, followed by sessions
that are not bound to a project. `SidebarConversations.vue` also assigns each
rendered row to a `projects` or `recents` zone and prevents dragging between
those scopes.

The hierarchy problem is presentational. The Projects label is rendered in the
main header, while the Recents label is generated by a CSS pseudo-element on
the first ordinary session. The count beside Projects is also sourced from the
total session count when there are no visible projects, so the number can
describe Recents while appearing to belong to Projects.

## Design

### Section presentation

- Render Projects and Recents with the same heading typography, alignment, and
  spacing so they read as peer sections.
- Keep the existing project-creation, search, and bulk-selection controls in
  the top header.
- Replace the Recents pseudo-element with a real presentational heading in the
  rendered list. This heading appears immediately before the first non-project
  session, or above the existing Recents empty state when there are none.
- Remove the pseudo-element spacing rules that make the first recent session
  responsible for drawing its own section title.

### Counts

- The Projects count is the number of rendered project workspace headers.
- The Recents count is the number of rendered session rows that are not members
  of a project.
- Counts are derived from the same filtered rows that are displayed, so a
  search/filter cannot leave a heading count inconsistent with its visible
  contents.
- A zero count is shown when the corresponding section is empty.

### Ordering and pinning invariants

No production ordering logic changes are required.

- Persisted projects remain before all non-project sessions.
- Pinning a non-project session moves it only to the front of Recents.
- Pinning a project session moves it only to the front of that session's own
  project; it does not move the project or cross into another project.
- Project pinning remains independent and continues to control project order.
- Manual dragging remains limited to the same project/Recents and pinned/
  unpinned scope.

The existing implementation provides these boundaries by sorting session
entries first and then rebuilding the rendered rows project-by-project before
appending non-project entries. The UI drag scope independently includes the
project identity (or `recents`) and pin group.

## Files and responsibilities

- `opensquilla-webui/src/components/SidebarConversations.vue`: derive visible
  per-zone counts and render the peer Recents heading without changing emitted
  events or row membership.
- `opensquilla-webui/src/assets/base.css`: style both headings consistently and
  remove the first-row pseudo-heading workaround.
- `opensquilla-webui/src/styles/apple-modern.css`: keep theme-specific heading
  sizing and spacing aligned for both sections if the base styles are
  overridden.
- `opensquilla-webui/src/components/SidebarConversations.workspaces.test.ts`:
  verify peer headings and independent visible counts.
- `opensquilla-webui/src/composables/useSessions.projects.test.ts`: lock the two
  pinning boundaries for persisted projects and ordinary sessions.

## Error handling and compatibility

The change introduces no network calls, persisted data migrations, or new
failure paths. Existing localization keys for Projects and Recents are reused,
so all supported languages retain their current copy. If the canonical project
list is unavailable, existing fallback grouping behavior remains unchanged.

## Verification

Use test-driven development:

1. Add failing component assertions for peer headings and separate counts.
2. Add failing arrangement tests proving ordinary and project session pins stay
   inside their respective scopes.
3. Implement the smallest template/computed-style change that satisfies the
   component assertions; ordering code should remain unchanged if the pinning
   tests confirm the reviewed behavior.
4. Run the focused component and composable tests, the full Web UI unit suite,
   type checking/architecture checks, and the production build.
